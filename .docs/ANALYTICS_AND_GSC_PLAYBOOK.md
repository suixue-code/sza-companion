# Search Console & 流量复盘（轻量手册）

在 GSC / Bing Webmaster 有数据后，用本清单做**每月一次**的复盘即可，不必每天刷。

**28 天基线表**（查询 + 网页 + 已编入索引 URL）：见 [GSC_BASELINE.md](./GSC_BASELINE.md) 与同目录 `gsc-baseline-*.csv`（从 GSC 导出后粘贴新行，保留旧快照对比）。

## Google Search Console

1. **效果**：看「查询」「网页」——哪些词已有展示、CTR 是否异常低（标题/描述是否匹配搜索意图）。
2. **编制索引 > 网页**：是否有「失败」「已发现尚未编入」——优先修首页、codes、两大工具页。
3. **编制索引 > 站点地图**：`sitemap-index.xml` 是否成功；若失败检查 `public/robots.txt` 与托管是否提供 `robots.txt`。
4. **体验（若有）**：核心网页指标是否全红——再针对性做性能，避免无数据时过度优化。

## Bing Webmaster Tools

1. 同步查看抓取与索引状态；提交同一站点地图 URL。
2. 若与 GSC 结论冲突，以**能否真实打开页面**为准排查 CDN/地区缓存。

## 如何把数据变成改站动作

| 观察 | 建议动作 |
|------|----------|
| `slime rng codes` 类查询展示高、点击低 | 更新 `site-meta.json` 日期；优化 codes 页标题/首段；核对 active 表 |
| 工具页有展示 | 检查预设说明是否过时；更新 `calculator-presets-meta.json` 或 `rebirth-goop-ladder.json` |
| 某篇 guide 突然无展示 | 是否被 `noindex`、死链、或与 canonical 冲突 |

## 排名更新窗口（核心更新 / 垃圾更新）

谷歌会在 [Search Status Dashboard · Ranking](https://status.search.google.com/products/rGHU1u87FJnkP6W2GwMi/history) 公布「core update」「spam update」等 rollout 窗口。此类更新**没有**单页「修复开关」，常见现象是全站或某类查询的展示/点击整体波动。

**建议在 rollout 标注完成后的 2～4 周内加频复盘**（例如每两周一次，而不仅是月底）：

1. **效果**：总点击、总展示是否突变；按「网页」筛出掉量最大的 URL。
2. **查询**：同一 URL 上，主查询词是否从「高意图词」换成了「泛词」——若是，优先检查标题/首段是否仍匹配原意图。
3. **技术**：索引失败、canonical、`hreflang` 是否与近期改版同时发生；若只有波动而无技术报错，避免盲目大改结构。

区分「正常波动」与「某模板页被整体削弱」：若掉量集中在**薄列表、无来源数字、与竞品高度同质**的页面，优先做内容侧「信息增益」（见下节），而不是堆 meta。

## 高展示、低点击：改什么（顺序建议）

1. **搜索结果里可见的标题与描述**：对照 GSC「查询」里该 URL 的前几名查询，问一句「用户搜这个词时点进来想立刻看到什么？」——先改 `<title>` 与 meta description（由页面 `BaseLayout` / 各页 frontmatter 传入）。
2. **首屏首段**：是否在 2～4 句内回答「这页是谁、解决什么、是否官方、数据多旧」；可参考站内 `.geo-snap` 文案模式（见首页、codes、wiki、工具组件）。
3. **数据新鲜度**：codes、预设批次、Goop 阶梯等是否已更新 `site-meta.json` / 对应 JSON 的核对日期。
4. **再考虑**大段加字或新路由：先确认不是标题/首段与意图错位导致的 CTR 问题。

## 信息增益自检（对抗同质摘抄）

在改长文或加新表前，用下面清单过一遍（不必写进页面，团队自检即可）：

| 问题 | 期望 |
|------|------|
| 这页是否比「复制一段 wiki」多一层？ | 至少有：**来源/置信度**、**与工具的内链**、或**可操作的步骤/表**。 |
| 数字从哪来？ | 能指到 `source-ledger`、manual ledger、或明确标为 estimate/low。 |
| 用户离开后能记住什么一句？ | 若答不出，说明首段与 H2 仍偏散。 |
